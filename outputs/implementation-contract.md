# 龙息：神寂装备计算器实施与验收合同

更新：2026-11-03

## 0. 当前判断

项目尚未完成。现有仓库证明了“公共资料可以编译、账号文件可以导入、组合可以求解”，但没有证明“真实登录账号可以被完整采集”。最终产品必须同时交付下列三个相互独立、可替换的模块；任一模块只有示例或脚手架都不算整体完成。

```text
公共数据编译器 ───────────────┐
                             ├─> 版本化 GameDataVersion
登录账号采集器 -> Staging ──┤
                 -> Review   └─> AccountSnapshot
                                      │
OptimizationRequest + HTML UI ────────┴─> Top N BuildResult
```

## 1. 成品 A：登录账号采集程序

### 用户 workflow

1. 用户在自己的客户端登录；采集程序不接收账号密码或令牌。
2. 用户选择渠道、客户端版本、语言和采集模式。
3. 首选模式为模拟器 ADB 可见画面：程序提示用户进入角色、装备、神器页面，首版由用户手动翻页并确认截屏。
4. 原图先保存为不可变证据；本地 OCR 产生文字与坐标，不上传图片。
5. 页面布局解析器把 OCR 行组合成角色、装备和神器 staging records。
6. 未识别、歧义或低置信字段进入 Review，不得静默猜值。
7. Review 完成后生成 `AccountSnapshot`；二次采集输出 merge/diff，而不是覆盖旧快照。

等级大于 1 的角色必须采集账号观测的无装备基础面板。公共目录的成长字段尚未证明能覆盖升星/灵感/渠道差异，默认求解器会阻止缺少 `baseStatsOverride` 的高等级角色；研究 CLI 只有显式开启未验证外推才可绕过。

### 必须采集的账号字段

| 对象 | 必填字段 | 重要可选字段 |
|---|---|---|
| 角色 | 稳定定义 ID、等级 | 星级、灵感、无装备面板、当前穿戴 |
| 装备 | 本地物品 ID/指纹、槽位、强化等级、主词条、全部副词条 | 套装、品质、锁定、穿戴者、名称 |
| 神器 | 稳定定义 ID、强化等级、精炼阶数 | 锁定、穿戴者、观察到的属性及置信度 |
| 快照 | 渠道、客户端版本、游戏数据版本、采集时间 | 源截图哈希、识别置信度、修订记录 |

### 首发实现路线

首发选择“Android 模拟器/设备 + ADB 截图 + Windows 本地 OCR + 人工 Review”。这条路线只读取用户主动展示的像素，不读内存、不抓包、不修改客户端。若目标环境只有官方 PC 客户端，则复用同一 Staging/Review/Finalize 管线，仅替换窗口截图适配器。

### 当前已有证据

- `collectors/account-collector.mjs`：操作者统一入口，提供渠道计划、引导采集、两级 Review pipeline 处理和状态摘要；不需要记忆内部脚本组合。
- `collectors/adb-session.mjs`：7 阶段、最低 50 张截图的引导式会话；只截屏，不点击。
- `collectors/cli.mjs ocr-bundle`：本机批量 OCR、文字坐标和不可覆盖派生文件。
- `collectors/cli.mjs extract-layout`：按版本化 layout profile 把坐标 OCR 转成 staging 和问题报告；目前仅有合成 profile 证据。
- `collectors/pipeline.mjs`：从截图 manifest 或 ADB capture session 一键运行到 OCR Review 门，应用逐行决策后继续到 staging Review 门，再执行 finalize/validate；全程按输入/产物哈希安全续跑。
- `window-screenshot`：官方 PC 候选入口，要求显式进程 PID，只截取可见未最小化窗口并保存边界/哈希元数据；能力探测已通过，真实客户端尚未验证。
- `window-session.mjs`：按独立 `channel=official_pc` 的 7 阶段 capture plan 引导用户手动导航和逐张截屏，最低数量不足时只能生成 partial manifest；dry-run 已验证，真实窗口会话待客户端。
- `prototype/staging-review.html`：第二级结构化字段编辑器，逐条修正三类账号实体、实时运行 canonical finalizer，并导出绑定 machine-staging SHA-256 的 `human_reviewed` 文件。
- `prototype/review.html`：原图关联、OCR 框、候选修正和接受/驳回。
- `collectors/cli.mjs finalize-staging`：已复核 staging 到 `AccountSnapshot` 的确定性转换。

### 尚缺且不能假装完成的部分

- 没有目标游戏真实截图，因此没有页面类型分类准确率。
- 通用布局解析器已实现，但没有按真实国服渠道/build 校准的角色、装备、神器 layout profile。
- 没有真实背包翻页覆盖和漏扫/重复检测结果。
- 本机没有 ADB 和游戏客户端，无法证明设备连接、分辨率适配或账号完整性。
- 国服中文名到 351 个公共角色 ID 的映射尚未建立。

### 完成门槛

在指定渠道和 build 上，使用测试账号重复执行两次：

1. 人工清点与采集输出的角色、装备、神器数量完全一致；
2. 关键字段逐项对照，无静默错误；
3. 重复截图不会产生重复物品；新增、强化、换装和删除能在 diff 中正确表现；
4. 所有低置信字段进入 Review；未解决字段阻止 finalize；
5. 生成的账号文件通过 Schema、语义校验并能被 HTML 直接导入。
6. 账号快照必须通过独立人工参考的完整性审计：三类总数、六槽位数量、角色/神器 ID 集合、重复与未知引用全部一致；仅 pipeline complete 不算采集完成。
7. 计算公式必须通过带渠道/build/来源证据的客户端面板 golden cases；synthetic formula cases 只能证明实现算术，不能作为客户端准确性证据。

## 2. 成品 B：公共游戏数据爬取与版本库

### 职责边界

公共数据回答“游戏里可能存在什么”，不包含“这个账号拥有什么”。它包括：

- 角色定义：名称与别名、元素、稀有度、基础属性、成长、技能和适用版本；
- 装备定义：槽位、品质、套装、主/副词条池、强化规则和变体；
- 神器定义：0–20 强化属性曲线、0–5 精炼效果文本、条件效果；
- 套装与规则：件数阈值、静态面板效果、条件战斗效果和叠加规则。

### 数据分层

```text
raw immutable snapshot
  -> source-specific parser
  -> corpus record with stable source ID
  -> reviewed canonical definition
  -> versioned GameDataVersion
  -> import dictionary / HTML data package / coverage report
```

`region + channel + season + clientBuild` 必须是版本键的一部分。当前文档不能倒推旧版本；社区来源不能冒充官方或客户端验证。

### 当前已有证据

- 已从不可变网页快照编译 351 个角色、682 个装备定义和 147 个神器。
- `GameData.equipment` 已正式输出 682 个装备定义；682 条具有完整强化曲线，677 条已有候选槽位，624 条关联套装家族。账号实例、OCR finalizer 与导入字典可通过稳定定义 ID 对齐。
- `equipment-rules.public.json` 已从带哈希的官方 Wiki 规则页整理 5 组副词条初始 roll/单次强化增量、4 组主属性里程碑和 3 条机制公式候选；强化事件总次数保持未知，未启用为自动推断。
- 147 个神器具有公共主属性与独立的强化/精炼记录。
- 已保存 70 条社区中文角色名和 6 条官方页面名称观察，但没有猜配稳定 ID。
- HTML 使用的公共数据包由编译器生成，不是单独手写副本。

### 尚缺

- 当前国服客户端的 build、名称、装备池和数值交叉验证；
- 5 个特殊装备定义的槽位映射；
- 国服完整角色/神器/套装别名；
- 完整随机副词条池、强化事件总次数/概率与合法 roll 的当前客户端证据；
- 大多数套装/神器条件效果仍是文本，只有 4 个套装效果可执行。

### 完成门槛

每个进入计算的字段必须能回溯到 URL、本地快照、具体记录和证据等级。每个发布数据包提供覆盖率、未映射项、矛盾和适用 build；与客户端不一致的记录必须隔离到不同版本，不能用“最新”覆盖历史。

## 3. 成品 C：账号文件导入 HTML 配装器

### 用户 workflow

1. 导入 `AccountSnapshot`，先显示版本、数量、警告和校验错误。
2. 选择账号拥有的角色和神器。
3. 固定神器；按需固定头、手、胸、武器、正位符文和负位符文。
4. 选择候选策略：只用未穿戴、允许拆指定角色、允许拆全部角色、排除锁定物品。
5. 添加任意数量的属性条件，例如：重击率 ≥ 100%、攻击 ≥ 5000、生命 ≥ 60000、命中 ≥ 150。
6. 选择最大化或最小化目标，或选择透明公式模板。
7. 查看 Top N、属性余量、换装清单、套装来源、搜索量和未建模效果。

### 当前可执行能力

- HTML 可导入账号 JSON，选择账号角色和神器，固定六个装备槽位；
- 优化目标可选择单属性、自动注入 100% 重击硬约束的满暴攻击×爆伤代理、不强制满暴的期望重击代理，或十项面板属性的自定义加权组合；百分比权重按页面显示的 1% 单位输入；
- 十种面板属性支持 `>=`、`>`、`<=`、`<`、`=` 及同属性区间；
- 每种属性可最大化/最小化，另有满暴输出代理；
- 小背包使用精确枚举，输出 Top 20 和理论上下限无解诊断；
- 中等空间可使用全局精确 Top N 分支定界；大空间自动使用明确标记的候选缩减启发式，用户可强制较慢的精确模式；
- CLI 与 HTML 共用同一个纯求解核心。

### 尚缺

- CSV 导入与批量编辑；账号库存编辑、merge/diff 已有可运行页面；
- 更完整的多角色换装冲突工作流；当前穿戴对比、拆装范围和锁定物品策略已可执行；
- 用户可编辑的加权目标和技能/战斗场景模型；
- 已有 100/300/1,000 件合成规模基准；仍缺真实大背包基准、启发式质量样本扩充和 Web Worker，当前同步求解可能阻塞 UI；
- 客户端公式校准；当前“爆伤 × 攻击”只是明确标注的面板代理，不是 DPS。

### 完成门槛

同一 `GameDataVersion + AccountSnapshot + OptimizationRequest` 在 HTML 和 CLI 中产生一致结果；小样本必须与暴力枚举 oracle 一致。至少使用一份真实账号快照验证固定项、门槛、Top N、无解诊断和换装清单，且所有结果明确数据版本和未建模项。

## 4. 统一数据契约

### `GameDataVersion`

只读、可版本化的公共定义。HTML 不从账号文件复制公共技能或套装说明，而是通过稳定 ID 引用对应版本。

### `AccountSnapshot`

用户拥有资产的本地快照。核心数组为：

```json
{
  "gameDataVersionId": "...",
  "ownedHeroes": [],
  "ownedGear": [],
  "ownedArtifacts": []
}
```

每件拥有物使用账号内 ID/指纹；公共名称、图标、基础定义通过 definition ID 查询。

### `OptimizationRequest`

保存角色、固定/排除项、候选策略、硬约束、目标和 Top N。请求文件可复算，不能只保存一张结果截图。

### `OptimizationResult`

保存选中物品 ID、最终属性、约束余量、套装、分数、搜索统计、数据版本、公式版本和警告。

## 5. 下一轮实施顺序

### M1：把文件导入闭环做成可交付 MVP

- 账号库存编辑器已落地；继续增加 CSV 模板和批量编辑；
- 导入 merge/diff、当前穿戴范围、锁定过滤和固定项覆盖已落地；继续补批量编辑与更完整的换装工作流；
- 100–1,000 件合成速度基准及一组 60 件精确质量对照已落地；继续增加分布/目标/约束矩阵和真实背包基准；
- 为每个目标保存可复算请求文件。

### M2：取得国服 golden screenshots

- 渠道/build 1 张；角色列表 1 组；角色详情 5–10 张；
- 六槽位装备详情 30–50 张；神器详情 10 张；
- 至少 3 组穿戴前后面板对照。

### M3：校准真实布局解析并生成账号快照

- 按页面类型建立版本化 layout profile；
- OCR 行聚合、字段规则校验、低置信 Review；
- 物品指纹、翻页覆盖、重复/漏扫检测；
- 与人工清点做完整性报告。

### M4：校准公式和公共数据

- 用无装备角色面板拆分基础值、百分比与固定值；
- 验证神器、套装和符文计数顺序；
- 把验证结果写回规则数据与 golden tests，而不是只改报告。

## 6. 现阶段可诚实演示的闭环

```text
不可变公共网页快照
  -> 公共定义编译器
  -> GameDataVersion

合成坐标 OCR -> 合成 layout profile -> OcrStaging
手工 OcrStaging
  -> validator + finalizer
  -> AccountSnapshot

AccountSnapshot + OptimizationRequest
  -> HTML/CLI solver（exact / bounded / heuristic 显式标记）
  -> BuildResult
```

这个闭环证明软件边界和计算方式可行，但其中的账号输入仍是合成/手工数据。只有 M2/M3 在真实客户端上通过后，才能把第一行改写成“登录账号采集程序已完成”。
