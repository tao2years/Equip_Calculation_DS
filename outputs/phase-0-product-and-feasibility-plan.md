# 龙息：神寂装备计算器 Phase 0 产品定义与可行性方案

更新：2026-11-03

## 执行摘要

建议把产品定义为一个**本地优先、可审计、可解释的账号装备求解器**：用户导入自己拥有的角色、装备和神器，选择角色与场景，固定任意槽位，设置属性下限/上限，再从账号真实库存中计算 Top N 配装。首版不追求完整战斗模拟，也不替用户操作游戏。

项目总体可行，但必须拆开看：

1. **求解器可行，风险低**。七个槽位、套装阈值、属性约束和目标函数都是成熟的组合优化问题。
2. **静态游戏数据可行，但版本治理工作量大**。公开 Wiki 已足以验证七槽位、主要属性、部分强化和套装规则；当前目录同时出现赛季、`+` 变体和 Reborn 内容，必须建立国服/国际服/渠道/赛季/build 维度。
3. **自动拉取玩家背包是项目最大不确定性**。Unity/IL2CPP 文件结构只能证明有研究入口，不证明能安全、稳定或合规地读取账号。现行条款对 reverse engineering、datamine、运行时交互数据与未授权第三方工具限制较宽。
4. **因此路线不能被“自动抓取”单点卡死**。MVP 先交付 JSON/CSV + 手工编辑器；第二步做用户主动截图 OCR；官方接口若未来存在，可无缝替换为新适配器。抓包、内存读和注入不进入默认路线。

## 1. 产品定位

### 核心用户任务

> 在不手工遍历几千种组合的情况下，用我账号里真实拥有的装备，为指定角色找到满足属性门槛的最佳方案，并且允许固定神器或任意装备。

### 一句话产品

“导入账号资产 → 选择角色和场景 → 锁定/排除装备 → 设置属性约束与优化目标 → 获得可解释的 Top N 配装。”

### 不做什么

- 不自动战斗、不自动穿戴、不发送游戏请求。
- MVP 不宣称精确 DPS；先提供面板与透明的输出代理。
- 不以账号密码、令牌或修改游戏进程换取导入便利。
- 不在第一版做阵容推荐、全模式攻略、排行榜等与核心闭环无关的“大而全”功能。

## 2. MVP workflow

### A. 账号数据中心

1. 创建本地账号档案。
2. 导入标准 JSON/CSV，或在表格编辑器中录入/粘贴。
3. 系统先进入 Staging：检查未知名称、非法槽位、百分比单位、重复装备、主副词条冲突和低置信 OCR。
4. 用户确认后生成不可变 `AccountSnapshot`；后续导入做 merge/diff，不覆盖历史。

### B. 配装工作台

1. 选择角色和成长状态。
2. 选择预设：重击输出、精通输出、坦克、命中辅助、纯面板或自定义。
3. 固定神器（默认常用操作），也可固定任意装备。
4. 选择候选范围：仅背包、允许拆指定角色、允许拆所有角色；尊重装备锁。
5. 添加硬约束：如重击率 ≥ 100%、攻击 ≥ 5000、生命 ≥ 60000、命中 ≥ 150。
6. 选择目标：最大攻击、生命、防御、爆伤、命中或“满暴下攻击 × 重击倍率”等。
7. 查看 Top N，比较当前方案、约束余量、换装清单、套装效果和未建模效果。
8. 保存/分享 build 文件；不自动回写游戏。

### C. 无解诊断

若没有可行组合，不显示空白结果，而显示：

- 每项约束的理论上限与缺口；
- 哪个锁定项/候选范围造成冲突；
- 最小放宽建议；
- “最接近的 5 套”及违反哪些条件。

## 3. 功能优先级

### P0 — 可用闭环

- 版本化静态数据包与别名表；
- 角色、装备、神器手工编辑；
- JSON/CSV 导入导出、错误修复、快照与差异；
- 单角色七槽位求解；
- 固定/排除物品，背包/拆装范围；
- 任意属性 min/max 约束；
- L0 面板目标与 L1 透明代理目标；
- Top N、对比当前方案、无解诊断；
- 本地数据存储与备份。

### P1 — 降低录入成本

- 单张/批量截图 OCR；
- OCR 置信度、规则校验和人工修复；
- 角色、装备和神器 merge；
- 装备评分、筛选、重复和可能出售标记；
- 预设场景与社区可分享的目标模板。

### P2 — 深度优化

- 多角色顺序锁定与小队联合分配；
- 指定技能/循环模型；
- 套装/神器条件 uptime；
- 更完整的角色技能、灵感、队长技和队伍 buff；
- 桌面扫描助手（只在条款复核和 OCR 达标后评估）。

### 暂不纳入

- 内存读取、代理抓包、证书绕过、DLL 注入；
- 自动点击穿戴、自动战斗；
- 云端托管用户完整账号数据；
- 未经许可再发布游戏美术与完整数据镜像。

## 4. 信息架构

```text
账号
├─ 导入与修复
├─ 角色
├─ 装备
├─ 神器
└─ 快照/备份

配装工作台
├─ 角色与场景
├─ 固定/排除
├─ 属性约束
├─ 优化目标
└─ 结果与比较

数据与设置
├─ 游戏数据版本
├─ 目标模板
├─ 单位/语言
└─ 隐私与诊断日志
```

首版推荐桌面 Web UI 或可安装 PWA：求解可放 Web Worker/WASM，用户数据默认留在本机；OCR 若需要原生截图与窗口控制，再提供独立桌面 companion，而不是把高权限塞进主应用。

### 推荐技术形态

第一版建议采用 TypeScript monorepo，先让领域模型、校验、计算和 UI 共用类型；当真实库存基准证明 JavaScript 搜索不够快时，再把纯求解内核迁到 Rust/WASM，而不是一开始承担双语言成本。

```text
apps/web              本地优先 UI（React + Vite/PWA）
apps/cli              批量导入、校验、基准与研究工具
packages/domain       无框架领域类型与单位
packages/game-data    版本化静态数据包与别名
packages/importers    manual/json/csv/ocr adapters
packages/calc         面板、套装、神器和 scenario 计算
packages/solver       枚举 oracle、剪枝求解、Top N
packages/schema       JSON Schema + runtime validation
packages/fixtures     golden cases、匿名样本与性能基准
optional/desktop      仅在需要原生截图/OCR 时引入 Tauri companion
```

- Web 端账号数据可先存 IndexedDB，并始终支持完整 JSON 备份/恢复。
- 若引入桌面壳，使用 SQLite 保存快照与变更，不让 UI 组件直接读写数据库。
- OCR 服务只产生 staging records；不能绕过 canonical validator 直接写入账号库。
- 静态数据包按 `region/release_line/season/build` 发布，应用允许并存与回滚。
- 计算和求解在 worker 中运行，主线程只负责交互；长任务可取消并报告阶段进度。

这只是推荐基线，不是不可变技术决策；在取得真实截图和 1,000–5,000 件库存基准前，不锁定 OCR 引擎和高性能求解语言。

## 5. 数据架构

### 三个边界

```text
Versioned Game Data (read-only)
          +
Account Snapshot (user-owned, local)
          +
Scenario / Objective / Constraints
          ↓
Calculation Engine (pure, deterministic)
          ↓
Explainable Build Results
```

### 关键原则

- 显示名不是 ID；中文、繁中、英文作为 aliases。
- flat 与 percent 不混用；百分比 canonical 值用小数（100% = 1.0）。
- 原始显示值、规范值、来源和置信度同时保存。
- 账号快照引用具体 `game_data_version_id`。
- 套装静态加成与战斗条件效果分开。
- 计算引擎是纯函数，同一输入必须得到同一输出。

初稿 schema 见 `schemas/account-snapshot.schema.json` 与 `schemas/optimization-request.schema.json`。

## 6. 计算模型

### 第一阶段：面板计算

需要客户端 golden case 验证最终公式。实现上把“角色基础”“百分比区”“固定值”“静态套装/神器”分层保存，避免过早把不确定的相加顺序固化。

### 满暴输出代理

当 `crit_rate >= 1.0`：

```text
score = attack * (1 + crit_damage)
```

非满暴时：

```text
score = attack * (1 + clamp(crit_rate, 0, 1) * crit_damage)
```

这个分数只能比较面板分布，不能当作 DPS。衍生伤害不能重击，因此精通流必须使用另一套目标模板。

### 求解器

- 槽位预筛选；
- stat vector 和套装 signature 预计算；
- meet-in-the-middle；
- Pareto dominance 删除全面劣势组合；
- 上界剪枝；
- Top N 稳定排序；
- 保存 exact/heuristic、搜索量、剪枝量与耗时。

先用小数据暴力枚举做 oracle，证明优化算法不漏最优解，再做性能优化。

## 7. 数据获取策略

### 静态数据

第一选择是可公开访问且许可清晰的官方资料；公开 Wiki 用于发现和交叉验证。若未来拥有官方客户端，可在单独实验仓库中验证资源结构，但不得因此默认获得再发布许可。

当前 Steam 文件清单表明 PC 客户端为 Unity/IL2CPP，存在 `StreamingAssets` 与 IL2CPP metadata。这使静态配置研究“技术上值得验证”，但条款风险意味着不能直接把反编译设为产品依赖。

### 用户数据

推荐顺序：

1. 官方 API/导出（若未来确认存在）；
2. 标准 JSON/CSV；
3. 手工编辑/粘贴；
4. 用户主动提供截图 OCR；
5. 仅在合规确认后评估可见 UI 自动导航。

项目应该先证明计算价值，再证明扫描便利性。即使自动导入最终不可行，产品仍可通过批量截图或表格粘贴完成闭环。

## 8. 同类产品启示

- **Fribbels**：目标、过滤、保持当前装备、导入 merge 和结果表格是一套成熟 workflow。
- **Genshin Optimizer**：扫描器与优化器由标准格式解耦；多目标适合后期，但模板复杂度会劝退新用户。
- **Inventory Kamera / GOODScanner**：OCR 必须结合词典、合法 roll 和交互修复，不能只追求“识别出文字”。
- **Summoners War Optimizer**：最低/最高属性、背包与拆装范围、broken set 都是高价值控制项。
- **yyshub.top**：本轮后台抓取没有读到其应用内部内容，因此仅把用户描述的整体心智模型作为参考，未声称已核验其功能或实现。

## 9. 里程碑与退出条件

### Phase 0 — 产品与规则基线（当前）

交付：仓库契约、研究协议、Wiki、来源台账、产品定义、schema 草案、风险门。

退出条件：目标地区/渠道明确；获得一组可公开或获授权的截图样本；核心属性与强化规则列出验证计划。

### Phase 1 — 单角色 MVP

交付：手工/JSON 导入、单角色求解器、固定装备、硬约束、Top N、无解诊断。

退出条件：

- 50+ 个 golden cases 全通过；
- 小背包结果与暴力枚举一致；
- 1,000 件库存常用查询达到交互级响应目标（建议 < 2 秒，最终由设备基准校准）；
- 所有结果包含数据版本和公式说明。

建议开发顺序：

1. 用 10–20 件虚构装备建立 schema fixtures；
2. 实现纯面板计算和全量暴力枚举 oracle；
3. 实现 JSON 导入、修复与快照；
4. 实现固定装备、min/max 约束和 Top N；
5. 加入套装 signature 与无解诊断；
6. 最后用真实匿名样本做公式校正和性能剪枝。

### Phase 2 — OCR

交付：截图批量导入、置信度、修复 UI、merge/diff。

退出条件：关键字段整件完全正确率达到约定门槛；不合格样本可定位和重试；任何低置信字段不会静默进入 canonical snapshot。

### Phase 3 — 多角色

交付：依次锁定、小队联合优化、装备冲突解释。

退出条件：多角色物品排他正确；可中断；近似算法有质量边界或基准对照。

### Phase 4 — 数据接入实验

只有在适用条款、账号风险和授权明确后启动。任何高风险路径失败都不阻塞主产品。

## 10. 主要风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 国服与国际服数值不同 | 算错且难发现 | 版本维度、不同数据包、截图 golden cases |
| Wiki 过时或字段翻译错 | 数据污染 | 多来源交叉、原文保留、状态标签 |
| 自动导入违反条款/触发风控 | 账号损失 | 默认不用抓包/内存/注入；测试账号；条款门 |
| OCR 误识别百分号/小数 | 推荐结果错误 | 合法值校验、置信度、人工确认 |
| 组合爆炸 | 卡顿或内存过高 | 预筛、MITM、Pareto、上界剪枝、worker |
| “输出最高”定义含糊 | 推荐误导 | 目标模板列明公式与未建模项 |
| 条件套装当成常驻 | 分数虚高 | sheet/conditional/encounter 三层模型 |
| 再发布游戏数据/图片的许可问题 | 发布受阻 | 开发数据与分发资产分开；上线前许可审查 |

## 11. 下一次 Review 需要的输入

1. 目标是国服腾讯客户端、国际服 Level Infinite、Steam，还是多个渠道？
2. 一组脱敏截图：角色面板 5–10 张、装备 30–50 件、神器 10 件，包含不同强化等级。
3. 用户真实最常用的 5 个目标模板及优先级。
4. 是否接受首版“截图/文件导入”，还是自动抓取是发布的硬门槛。
5. 产品只供自己/小圈子本地使用，还是计划公开发布；这会改变数据与美术许可要求。

## 12. 证据与限制

本阶段没有游戏客户端、没有账号、没有运行时实验。公开资料只能支撑产品模型和候选规则，不能证明国服当前数值或账号数据路径。详细来源状态见 `corpus/source-inventory.csv`；未决问题见 `state/open-questions.md`。
