# 研究协议

## 目标

把游戏规则、客户端可获取性、同类产品经验和实验结果编译为可持续维护的装备计算知识库，为产品和实现提供同一事实源。当前不是一次性“抄 Wiki”，也不把社区攻略当作官方数值表。

## 研究问题

1. 哪些数据是稳定的静态规则，哪些随地区、赛季、客户端版本或角色状态变化？
2. 能否在不接触凭据、不修改客户端且风险可接受的前提下获取玩家角色和装备？
3. 如何准确表达角色面板、装备词条、神器效果、套装条件、战斗条件与目标函数？
4. 如何在用户可理解的时间内找到满足硬约束的最优或近似最优组合？
5. 产品如何解释“为什么推荐这套”，并让用户复核数据和假设？

## 证据等级

| 等级 | 类型 | 可支持的结论 |
|---|---|---|
| E1 | 当前官方客户端实测、官方结构化数据或官方明确规则 | 当前指定版本行为 |
| E2 | 官方 Wiki、官方公告、官方商店与条款 | 当前公开描述；需注意更新时间与运营主体 |
| E3 | 可复现的只读实验、客户端公开文件清单 | 技术结构或观察结果，不自动代表服务端规则 |
| E4 | 高质量开源工具、社区 Wiki、攻略与多方一致报告 | 线索、交互模式、待验证规则 |
| E5 | 研究推断或产品建议 | 只能标记为推断/建议，不能冒充游戏事实 |

## 版本维度

每个规则或实体至少允许记录：

- `region`: `cn` / `global` / `unknown`
- `channel`: `official_pc` / `steam` / `android` / `ios` / `emulator` / `web`
- `release_line`: `legacy` / `reborn` / `unknown`
- `season`
- `game_build`
- `valid_from` / `valid_to`
- `retrieved_at`

未知值必须保留为 unknown，不能用抓取日期代替版本生效日期。

## 工作流

1. 从 `wiki/index.md` 和 checkpoint 确认当前问题。
2. 将来源加入 `corpus/source-inventory.csv`，分配稳定 ID 和覆盖状态。
3. 能合法固化的来源保存为带元数据的不可变快照；暂不能固化时记录 URL、定位和缺口。
4. 抽取到结构化实体，再更新主题 Wiki；不直接把网页段落当最终数据模型。
5. 对冲突按“地区/版本差异 → 翻译差异 → 页面过时 → 抽取错误”顺序调查。
6. 实验前写假设、输入、环境、停止条件和账号风险；实验后保存日志与失败结果。
7. 生成产品/开发输出，运行 schema、链接、覆盖和 golden-case 校验。
8. 追加日志并更新 checkpoint。

## 账号数据实验红线

- 不采集登录密码、验证码、支付信息或可复用会话令牌。
- 不绕过 TLS、证书固定、反作弊或访问控制。
- 不注入 DLL/so、不修改进程内存、不伪造请求、不自动执行游戏行为。
- 任何可能触发封号的实验只允许在明确授权的隔离测试账号上进行，并且需要当前条款复核。
- 优先顺序：官方导出/API → 用户文件 → 用户主动截图 OCR → 只读可见 UI 辅助 → 其余路径默认停止。

## 完成度标签

`discovered` → `captured` → `screened` → `modeled` → `cross_checked` → `runtime_validated`

任何汇总都必须按标签报告覆盖，禁止把“找到页面”说成“数据已验证”。
