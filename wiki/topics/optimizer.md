# 配装求解与结果解释

## 当前可执行入口

浏览器和 CLI 共用 `prototype/optimizer-core.mjs`，防止两端产生不同公式。CLI 接受版本化账号快照和 `OptimizationRequest`：

```powershell
node scripts/solve_request.mjs --account account.json --request request.json --output result.json
```

当前执行器支持六装备槽的完整枚举、全局精确 Top N 分支定界和快速启发式候选缩减，另支持固定神器/任意装备、排除物品、背包/指定角色/全部角色候选策略、锁定过滤、所有 sheet 层比较运算符、单属性、加权属性及重击输出代理目标。每次结果携带求解模式和精确性标志；`conditional` 和 `encounter` 层会明确拒绝，直到对应战斗模型存在。

## 问题定义

对每个未固定槽位选择一件账号已有物品，在不重复占用的前提下，激活对应套装和神器效果；先满足全部硬约束，再按目标函数排序。单角色首版只处理一个角色，神器通常固定；多角色版本再加入跨角色物品排他与优先级。

## 用户可理解的 workflow

1. 选择账号快照与数据版本。
2. 选择角色和角色成长状态。
3. 选择场景模板：纯面板、重击输出、精通输出、坦克、命中辅助，或自定义。
4. 固定神器/装备，设置“可拆其他角色装备”“仅背包”“排除某套装”等候选范围。
5. 添加硬约束，例如重击率 ≥ 100%、攻击 ≥ 5000、生命 ≥ 60000、命中 ≥ 150。
6. 选择目标：最大某属性、加权评分、平均重击伤害、指定技能/循环。
7. 运行求解，返回 Top N、与当前方案差值、使用了哪些已穿戴装备、约束余量和触发假设。
8. 保存方案；首版只导出/展示，不自动回写游戏。

## 目标函数分层

### L0：面板目标

- 最大 `atk_sheet`、`hp_sheet`、`def_sheet`、`crit_rate`、`crit_damage`、`accuracy` 等。
- 可直接验证，适合 MVP。

### L1：代理输出目标

在“满暴”条件下，用户提出的“爆伤 × 攻击”可以写成：

```text
score = atk_sheet * (1 + crit_damage)
constraint: crit_rate >= 1.0
```

若不是满暴，较合理的期望重击代理为：

```text
expected_crit_multiplier = 1 + min(max(crit_rate, 0), 1) * crit_damage
score = atk_sheet * expected_crit_multiplier
```

这仍不是游戏总 DPS，因为没包含技能倍率、增伤区、敌方防御、攻击速度、循环、条件 uptime 和衍生伤害。UI 必须把它叫“面板输出代理”，不能叫精确 DPS。

### L2：技能/循环模型

用角色技能倍率、技能急速、攻击速度、队伍效果和条件权重计算单技能或加权循环。每个模板需版本化并列出假设；衍生伤害与重击伤害必须分开。

## 约束 DSL（产品层）

首版不用暴露代码，内部可表达为：

```json
{
  "all": [
    {"stat": "crit_rate", "op": ">=", "value": 1.0},
    {"stat": "atk_sheet", "op": ">=", "value": 5000},
    {"stat": "hp_sheet", "op": ">=", "value": 60000},
    {"stat": "accuracy", "op": ">=", "value": 150}
  ]
}
```

另支持固定 `owned_item_id`、限定/排除套装、限定主词条、是否允许拆装和物品锁定。

## 求解策略

### 当前实现

- 搜索空间不超过 10 万时完整枚举，满足数量、极值和 Top N 都精确。
- 中等规模使用安全属性上下界做 branch-and-bound；Top N 全局精确，但分数剪枝后满足数量只保留已确认下界，极值为安全边界。
- 搜索空间超过 500 万时，自动模式按目标、约束和套装代表缩减到每槽最多 10 件，再做有界搜索；此模式属于 heuristic，不保证完整背包全局最高。
- 用户可在 HTML 中显式选择自动、全局精确 Top N 或快速启发式；CLI 可强制完整枚举用于 oracle。
- 每次保存原始/缩减搜索空间、评估叶节点、访问节点、约束剪枝、分数剪枝和精确性标志。

合成规模证据见 [求解器合成规模基准](../../outputs/optimizer-scalability-benchmark.md)。100/300/1,000 件合成背包的自动启发式模式均在本机约 0.5–1.0 秒返回；60 件质量样本中第一名分数与精确模式一致、Top 20 重合 18/20。它只证明当前合成分布下的速度与一例质量，不代表真实账号或普遍误差保证。

### 规模扩大后

- 单角色：meet-in-the-middle + Pareto dominance 通常比盲目笛卡尔积更合适。
- 多角色：外层做角色顺序/物品排他分配，内层复用单角色候选池；可提供“逐个锁定”和“小队联合优化”两种模式。
- 复杂条件效果：先把条件参数化为 scenario，避免在核心搜索循环里运行任意脚本。

## 准确性与可解释性

每个结果展示：

- `exact` / `bounded` / `heuristic`
- 游戏数据版本和账号快照时间
- 目标公式与硬约束
- 静态、条件和未建模效果
- 各槽贡献、套装贡献、相对当前装备变化
- 未满足时的最近解与每个约束缺口

用户更需要“为什么没有结果”而不是空表。若约束不可行，应给出冲突诊断，例如“命中还差 12；放宽生命到 58,400 后有 27 套可行解”。

## 校验计划

1. 人工构造小背包穷举，验证剪枝结果等于暴力最优。
2. 对每种套装阈值建立 golden cases。
3. 用游戏面板截图对角色 + 装备加总做逐项对照。
4. 属性公式和技能模板分别测试，避免“组合正确但公式错误”。
5. 合成性能基准已覆盖 100、300、1,000 件；仍需真实背包以及 5,000 件压力样本。
