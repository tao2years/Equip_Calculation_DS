# 决策记录

## D-001 · 本地优先

- 日期：2026-11-03
- 状态：accepted
- 决策：账号快照、截图和求解默认只在本机处理；云同步不是 MVP 前置条件。
- 原因：降低隐私、凭据和分发风险，也允许离线使用。

## D-002 · 数据接入适配器化

- 日期：2026-11-03
- 状态：accepted
- 决策：手工、JSON/CSV、OCR 和未来官方接口统一输出 canonical account schema。
- 原因：账号自动获取存在技术与条款不确定性，不能与求解器耦合。

## D-003 · 高风险导入路径默认禁用

- 日期：2026-11-03
- 状态：accepted
- 决策：抓包、内存读取、TLS 绕过、注入和客户端修改不进入默认路线。
- 原因：当前条款证据显示限制广泛，且本阶段没有隔离账号或客户端。

## D-004 · 先面板、后战斗模拟

- 日期：2026-11-03
- 状态：accepted
- 决策：MVP 支持面板目标和透明代理目标；精确技能/循环模型后置。
- 原因：先验证数据和组合正确性，避免不透明的伪精确 DPS。

## D-005 · 结果必须可解释

- 日期：2026-11-03
- 状态：accepted
- 决策：每个结果必须带版本、目标、约束、锁定项、条件假设和 exact/heuristic 状态；无解必须诊断缺口。

## D-006 · OCR 采用三段式证据链

- 日期：2026-11-03
- 状态：accepted
- 决策：原始截图、机器 recognition bundle、人工 Review 决策分开保存；只有布局解析和语义校验通过后才生成 `OcrStaging`/`AccountSnapshot`。
- 原因：字典命中不等于字段归属，分层可保留原证据、复算 OCR、审计修正并避免低置信结果静默进入求解器。

## D-007 · 布局规则按渠道和 build 版本化

- 日期：2026-11-03
- 状态：accepted
- 决策：OCR 坐标、页面锚点和字段必填规则保存为独立 layout profile，并显式记录渠道、客户端 build、语言和证据等级；合成 profile、真实 golden screenshot profile 与运行时验证状态不得混用。
- 原因：客户端 UI、分辨率、地区翻译和版本更新都可能改变字段位置。把坐标写死进采集器会让旧规则静默污染新账号快照。
- 限制：在拿到客户端稳定物品 ID 之前，内容指纹无法区分两件视觉完全相同的装备；当前策略是报告冲突并阻止静默去重。

## D-008 · 求解精确性必须随规模显式降级

- 日期：2026-11-03
- 状态：accepted
- 决策：小空间完整枚举；中等空间用安全上下界返回全局精确 Top N；超大空间自动缩减候选并标为 heuristic。界面和结果文件必须分别记录 Top N、满足数量和极值是否精确，禁止把启发式推荐称为全局最高。
- 原因：六槽位笛卡尔积在 1,000 件合成库存上约为 21.4 万亿套。同步完整搜索不适合作为默认交互，而未经标记的候选裁剪会制造伪精确结果。

## D-009 · 采集管线默认保留两级人工 Review 门

- 日期：2026-11-03
- 状态：accepted
- 决策：一键采集程序在 recognition 后先等待逐行 OCR Review，应用接受/驳回和唯一候选决策后才做布局解析；machine staging 产生后再等待字段级 Review。只有两级通过才能 finalize。自动接受开关只允许 synthetic fixture。
- 原因：OCR 字典命中和坐标字段归属是两个独立错误面。自动化编排不能把任一层校对降格成无法参与后续流程的旁路报告。

## D-010 · 神器强化与精炼分轴，账号观测优先

- 日期：2026-11-03
- 状态：accepted
- 决策：`level` 表示 0–20 强化等级并选择静态面板曲线；`refinement` 表示 0–5 精炼阶数并选择效果文本。账号直接观测到的静态属性优先于公共曲线，但必须保留来源和差异警告。
- 原因：公共数据明确包含两套不同长度的数据。把二者合并会选错属性；把公共属性复制到账号快照则会掩盖版本冲突。条件效果未完成场景建模前不进入常驻面板。

## D-011 · 公共装备定义与账号实例分离

- 日期：2026-11-03
- 状态：accepted
- 决策：`EquipmentDefinition` 进入版本化 `GameData`，保存所有账号共享的名称、槽位、套装、品质、赛季和主属性曲线；`OwnedGear` 只保存账号内物品 ID、随机属性、强化、锁定和穿戴关系，并通过可选 `definitionId` 引用公共定义。
- 原因：把 682 条公共装备只留在编译中间层，会让采集器和 HTML 重复名称/槽位/套装；反过来把随机实例属性放进公共定义，会错误地认为所有账号拥有相同词条。同名歧义必须保留为 Review 问题。

## D-012 · PC 客户端采集先采用显式窗口只读截图

- 日期：2026-11-03
- 状态：accepted
- 决策：官方 PC 候选适配器只接受用户明确提供的进程 PID，只截取当前可见且未最小化的主窗口，不枚举其他窗口、不自动点击或登录；截图与边界、SHA-256 和限制说明成对保存。
- 原因：这能复用既有 OCR/Review 管线，同时把账号凭据、进程内存、网络流量和输入自动化排除在默认范围外。`CopyFromScreen` 会受到遮挡、DPI 和全屏模式影响，因此能力探测不等于真实客户端已通过。

## D-013 · Pipeline complete 不等于账号采集完整

- 日期：2026-11-03
- 状态：accepted
- 决策：真实采集必须额外提供独立人工清点 reference，并对三类资产总数、六槽位装备数、角色/神器 definition ID 集合、重复 owned ID、重复定义和未知公共引用做机器审计；任一不一致即失败。
- 原因：截图、OCR 和 Review 全部正常结束仍可能漏页、跳项或重复。只有与独立参考对账才能把“程序结束”提升为“当前参考范围内采集完整”，且通过报告仍不得声称人工参考本身绝对完整。

## D-014 · Synthetic 公式测试与客户端公式证据分级

- 日期：2026-11-03
- 状态：accepted
- 决策：公式验证输入必须记录 evidence level、地区、渠道、build 和来源证据；`synthetic_fixture` 只验证实现算术，只有 `client_observation` 的穿戴前后面板 case 才能支持对应渠道/build 的面板公式结论。
- 原因：单元测试通过并不证明游戏使用同一结算顺序。把二者分级可防止原型公式和真实游戏规则混为一谈，并让未来客户端截图直接进入可复算误差报告。

## D-015 · 官方入口身份与数值正确性分开评级

- 日期：2026-11-03
- 状态：accepted
- 决策：Steam 官方公告可把 `dragonheir.info` 的来源类别确认为 `official_wiki`；但具体记录仍保留 `public_catalog_compiled_not_client_validated`，直到目标渠道/build 的客户端证据通过。
- 原因：官方入口背书解决来源身份问题，不会自动解决跨赛季、跨地区、翻译、更新延迟、数据许可或单条数值正确性。装备等级成长也不得被误解为随机副词条 roll 次数。

## D-016 · 副词条数值规则与强化事件次数分开建模

- 日期：2026-11-03
- 状态：accepted
- 决策：Wiki 明示的初始 roll 区间和“每次增加同额”可以进入独立公共规则包；来源未说明的强化事件总次数必须为 `null`。规则在目标客户端验证前不自动反推账号装备历史，也不直接影响求解结果。
- 原因：当前值可能由多种初始 roll 与强化落点组合产生。把等级上限、主属性成长档位或玩家经验当作副词条次数会制造无法追溯的伪精确数据。

## D-017 · 满暴目标由求解器强制约束

- 日期：2026-11-03
- 状态：accepted
- 决策：`full_crit_damage_proxy` 自动加入 `crit_rate >= 1.0`，目标为 `atk_sheet × (1 + crit_damage)`；该隐式约束必须进入结果文件和无解诊断。原 `crit_proxy` 保留为不强制满暴的期望重击代理。
- 原因：依赖 UI 预填条件会在用户删除条件、CLI 请求或其他调用端中失效，从而把非满暴方案误称为“满暴最优”。约束属于目标语义，应由共享求解核心保证。

## D-018 · 高等级角色默认要求账号观测基础面板

- 日期：2026-11-03
- 状态：accepted
- 决策：等级大于 1 且缺少 `baseStatsOverride` 时，库存校验和共享求解器默认失败。研究 CLI 可用 `calculationPolicy.allowUnverifiedHeroGrowth=true` 显式接受公共成长外推，但结果保留未验证来源。
- 原因：公共 `perLevelGrowth` 的精确含义、升星/灵感顺序和渠道适用性未验证；个别比例属性线性外推会产生明显不合理结果。继续静默计算比明确要求账号面板风险更高。

## D-019 · 套装文本只编译完整无条件静态句

- 日期：2026-11-03
- 状态：accepted
- 决策：公共套装效果只有在整句符合件数前缀、白名单属性、数值与单位规则时才进入 `sheetStats`；任一条件、触发、持续时间、未知词或单位错误都拒绝整句。原始效果文本始终保留，编译结果标记为官方 Wiki 文本解析且未客户端验证。
- 原因：静态两件套能显著扩大真实求解覆盖，但从自然语言局部抽取数字会把“触发后增加”等条件效果错误当作常驻面板。完整句白名单在覆盖率与证据纪律之间提供可复核边界。

## D-020 · 校准采样计划与全账号采集计划分离

- 日期：2026-11-03
- 状态：accepted
- 决策：统一账号采集器默认选择 `full_account`，要求角色/装备/神器列表完整到末尾，并逐个覆盖所有拥有对象详情；这些阶段必须显式输入覆盖确认。固定 50 张的 `golden_calibration` 只能用来校准 OCR/layout/公式，必须显式选择，不能生成全量完成结论。finalize 后仍需独立人工 reference 审计。
- 原因：最低样本数只能证明解析器见过若干页面，不能证明账号没有漏角色、漏装备或漏神器。把两种目的共用一个 complete 状态会造成危险的完成度误报。

## D-021 · 截图账号资产必须保留记录级证据引用

- 日期：2026-11-03
- 状态：accepted
- 决策：`screenshot_ocr` 来源的每条角色、装备和神器记录必须引用顶层 `sourceFiles` 中存在的 SHA-256，并保存文件名、序号、页面类型和 Review 状态。finalizer 必须保留引用，优化结果必须带回所选神器和六件装备的引用。手工/合成记录可无截图引用，但不能冒充截图采集。
- 原因：只有数值而没有原图关联时，OCR 错字、同形装备和人工修订无法审计；推荐结果也无法解释具体使用了哪张证据。
